# Tree Tracker API

Go-бэкенд Tree Tracker хранит рутины, их выполнения и единственное общее
состояние дерева. Фронтенд показывает это состояние как процедурно растущее
дерево: выполнение рутины начисляет очки и атомарно продвигает растение.

## Что работает сейчас

1. Пользователь создаёт рутину с категорией, весом и коэффициентом.
2. `POST /api/routines/{id}/complete` создаёт выполнение и увеличивает рост
   растения на `weight × coefficient` очков в одной транзакции.
3. `GET /api/plant` возвращает актуальные параметры дерева для рендера.
4. `GET /api/completions` возвращает историю выполнений демо-пользователя.

Текущая версия рассчитана на демонстрацию с одним общим деревом и временным
пользователем `00000000-0000-0000-0000-000000000001`. Аутентификации и
привязки растения к пользователю пока нет.

## Рост дерева

В базе характеристики дерева хранятся как целые значения от `0` до `100`, а
API отдаёт их как доли от `0` до `1`.

- Один этап роста содержит `100` очков.
- Фазы `0`–`3` последовательно описывают переход от ростка к живому дереву.
- После достижения фазы `3` каждые следующие `100` очков увеличивают `epoch`;
  сама фаза остаётся равной `3`.
- Баллы за выполнение вычисляются как `weight × coefficient`, где оба значения
  разрешены в диапазоне от `1` до `5`.
- Обычную рутину можно выполнить один раз в UTC-день. Одноразовую
  (`disposable: true`) — только один раз за всё время.

При выполнении рутины сервис блокирует строку растения (`FOR UPDATE`), создаёт
выполнение, пересчитывает `phase`, `phaseProgress` и `epoch`, затем коммитит
всё одной транзакцией. Повторное выполнение не меняет растение.

## Запуск

### Только API и PostgreSQL

Из каталога `tree-tracker`:

```bash
cp .env.example .env
docker compose up --build
```

Compose запускает PostgreSQL, контейнер миграций и API. Миграции применяются
до старта API. По умолчанию API доступен на `http://localhost:8080`, PostgreSQL
— на `localhost:5432`.

### Полный стек с frontend

Из родительского каталога проекта:

```bash
docker compose up --build
```

Будут запущены PostgreSQL, миграции, API и frontend. Значения по умолчанию:

- API: `http://localhost:8080`
- frontend: `http://localhost:8081`

Порты и данные PostgreSQL задаются переменными `API_PORT`, `WEB_PORT`,
`POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`.
Для запуска API вне Docker используются `API_HOST`, `API_PORT` и
`DATABASE_URL` из `.env.example`.

## API

Все ответы используют JSON с полями в `camelCase`.

### Растение

`GET /api/plant`

```json
{
  "epoch": 0,
  "phase": 1,
  "phaseProgress": 0.37,
  "branching": 0.48,
  "density": 0.71,
  "curvature": 0.22,
  "vitality": 0.91,
  "seed": 12345
}
```

Начальное состояние добавляется миграцией `000005_seed_plant` только если
таблица `plants` пуста.

### Рутины

`GET /api/routines` возвращает массив рутин.

`POST /api/routines` создаёт рутину:

```json
{
  "category": "health",
  "type": "Прогулка",
  "weight": 2,
  "coefficient": 1,
  "temporary": false,
  "disposable": false
}
```

Допустимые категории: `health`, `study`, `personal`. Поле `type` обязательно
и ограничено 100 символами; `weight` и `coefficient` находятся в диапазоне
`1..5`.

Ответ создания имеет статус `201`:

```json
{
  "id": 1,
  "category": "health",
  "type": "Прогулка",
  "weight": 2,
  "coefficient": 1,
  "timeType": {
    "temporary": false,
    "disposable": false
  }
}
```

В коде есть обработчики изменения и удаления, но их маршрут пока
зарегистрирован как `/api/routine` без параметра ID. Поэтому `PATCH` и
`DELETE` сейчас не являются рабочей частью HTTP-контракта; для изменения
рутин пока следует создать новую запись или изменить данные в БД.

### Выполнения и прогресс

`POST /api/routines/{id}/complete` отмечает выполнение рутины и продвигает
дерево. Тело запроса не требуется.

```json
{
  "id": 42,
  "routineId": 1,
  "completedAt": "2026-08-29T10:00:00Z"
}
```

Повторное выполнение возвращает `409`: для обычной рутины — если она уже
выполнена сегодня, для `disposable` — если она уже выполнена когда-либо.

`GET /api/completions` возвращает список выполнений текущего демо-пользователя.
Порядок списка сейчас определяется PostgreSQL, поэтому клиенту не следует
считать его отсортированным.

### Пользователи

Пользовательский модуль пока отдельный от прогресса дерева.

- `POST /api/user` — создаёт пользователя, пароль хешируется bcrypt.
- `GET /api/user` — ищет пользователя по `email` из JSON-тела запроса.
- `DELETE /api/user` — удаляет пользователя по `email` из JSON-тела запроса.

Логин, токены, авторизация и профиль ещё не реализованы. В частности, текущие
эндпоинты выполнений не используют созданного пользователя, а всегда работают
с временным UUID из обработчика.

## Хранилище и миграции

PostgreSQL состоит из таблиц:

- `plants` — единое состояние дерева и параметры его внешнего вида;
- `routines` — пользовательские действия и правила их начисления;
- `completions` — уникальные выполнения по `(user_id, routine_id, occurrence_key)`;
- `users` — заготовка пользовательских аккаунтов.

Миграции лежат в `migrations/` и применяются контейнером
`migrate/migrate:v4.19.1`. Для ручного запуска в Docker:

```bash
docker compose run --rm migrate
```

## Устройство кода

```text
cmd/api/                # создание зависимостей, роутер Chi, HTTP-сервер
internal/
├── plant/              # чтение состояния дерева и JSON-представление
├── progress/           # транзакция «выполнить рутину → вырастить дерево»
├── routine/            # создание и чтение рутин, их валидация
├── completion/         # HTTP-ручки и чтение истории выполнений
├── user/               # регистрация, чтение и удаление пользователя
└── config/             # переменные окружения
migrations/             # схема PostgreSQL и стартовое растение
```

HTTP-обработчики разбирают и проверяют запрос, сервисы содержат сценарии, а
репозитории работают с PostgreSQL. `progress.RepositoryDB` намеренно объединяет
запись выполнения и обновление растения: так операция остаётся атомарной.

Сервер использует `chi`, `pgxpool`, `slog`, request ID и panic recovery.
Таймауты HTTP: чтение — 10 секунд, запись — 20 секунд, idle — 120 секунд.

## Ближайшие ограничения

- Нет аутентификации и связи дерева с конкретным пользователем.
- Редактирование и удаление рутин требуют исправления HTTP-маршрута с ID.
- Значения параметров растения пока задаются миграцией и не меняются через API.
- `temporary` сохраняется в рутине, но ещё не влияет на правила выполнения или роста.
