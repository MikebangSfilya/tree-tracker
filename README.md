# Tree Tracker

## Временный набор технологий

- Go 1.25.
- PostgreSQL.

Набор технологий считается временным: изменения, завязанные на конкретные технологии,
должны быть простыми для замены после отдельного решения команды.

## Структура проекта

```text
cmd/api/main.go
internal/
├── user/
├── routine/
├── completion/
└── plant/
migrations/
```

`pkg/` не создаём, пока не появится действительно общий код, используемый
несколькими независимыми пакетами.

Каждый бизнес-модуль живёт в своей папке. Базовый состав модуля:

```text
internal/routine/
├── model.go       # доменные модели
├── requests.go    # входные HTTP-запросы и их структуры
├── service.go     # сценарии использования и бизнес-логика
├── repository.go  # хранение данных и работа с БД
├── handler.go     # HTTP-обработчики и регистрация маршрутов модуля
└── response.go    # ответы и преобразование результата в структуры ответа
```

Файлы добавляются только когда для них есть код. Название — `response.go`,
не `responce.go`.

Маршруты модуля собираются в его папке. `handler.go` содержит обработчики и
регистрацию маршрутов модуля; `cmd/api/main.go` только собирает зависимости
и подключает модули к общему маршрутизатору.

## Архитектура

- HTTP-обработчик не содержит бизнес-логики.
- Обработчик работает по цепочке: разобрать запрос → проверить данные →
  вызвать службу → вернуть ответ.
- Служба содержит сценарии использования и бизнес-логику.
- Репозиторий занимается только хранением данных.
- Модули не обращаются напрямую к таблицам друг друга.
- Зависимости передаются явно; глобальные клиенты базы данных и Redis запрещены.

## Ошибки

- Доменный слой и службы возвращают понятные ошибки.
- Преобразование ошибок в HTTP-ответ выполняется на границе приложения — в
  HTTP-слое.
- Сырой текст ошибки PostgreSQL клиенту не возвращается.

## Контекст выполнения

- `context.Context` — первый аргумент методов, которые обращаются к базе данных или
  сети.
- `context.Context` нельзя хранить внутри структуры.

## База данных

- Все изменения схемы выполняются только через папку `migrations/`.
- SQL не размазывается по обработчикам.
- Транзакция начинается на уровне сценария использования, которому действительно
  нужна атомарность.

## API

- Текущий JSON-контракт всегда использует `camelCase`:

  ```json
  {
    "completion": {
      "id": 42,
      "routineId": 7
    },
    "plant": {
      "epoch": 0,
      "phase": 1,
      "phaseProgress": 0.37,
      "branching": 0.48,
      "density": 0.31,
      "curvature": 0.22,
      "vitality": 0.94,
      "seed": 12345
    }
  }
  ```
- Ошибки возвращаются в едином формате.
- ID имеют один тип во всех слоях и модулях.
- Контракт API нельзя менять молча. Если контракт изменится, об этом будет
  сообщено отдельно.

## Код

- Перед коммитом запускать `gofmt` и `go vet`.
- Функции должны быть небольшими и делать одну понятную вещь.
- Интерфейсы обязательно объявляются в том пакете, который ими пользуется, а не
  «на всякий случай».
- Не создавать абстракции ради абстракций.

## Git и проверка изменений

- Одна задача — одна ветка.
- Запрос на слияние изменений должен быть небольшим и решать одну задачу.
- Изменения другого человека должен посмотреть хотя бы один участник.
- Нельзя отправлять изменения напрямую в `main`.
- Если меняется общий контракт, написать об этом в командный чат до объединения
  изменений.

## Если что-то неясно или не успеваешь

Нельзя молча оставлять проблему, делать предположения о критичной логике или
прятать незавершённую работу.

Если не понимаешь задачу, архитектурное решение или последствия изменения —
сначала спроси. Если не успеваешь закончить — заранее сообщи об этом и либо
передай задачу другому человеку, либо явно согласуй перенос срока. Передача
должна включать текущий статус, что уже сделано, что осталось и какие есть
блокеры.
