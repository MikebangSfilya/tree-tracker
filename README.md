# Tree Tracker

## Временный стек

- Go 1.25.
- PostgreSQL.

Стек считается временным: изменения, завязанные на конкретные технологии,
должны быть простыми для замены после отдельного решения команды.

## Структура проекта

```text
cmd/api/main.go
internal/
├── user/
├── routine/
├── completion/
└── plant/
migrations/
```

`pkg/` не создаём, пока не появится действительно общий код, используемый
несколькими независимыми пакетами.

Каждый бизнес-модуль живёт в своей папке. Базовый состав модуля:

```text
internal/routine/
├── model.go       # доменные модели
├── requests.go    # входные HTTP-запросы и их DTO
├── service.go     # use-case и бизнес-логика
├── repository.go  # persistence и работа с БД
├── handler.go     # HTTP handlers и регистрация маршрутов модуля
└── response.go    # ответы и преобразование результата в DTO
```

Файлы добавляются только когда для них есть код. Название — `response.go`,
не `responce.go`.

Маршруты модуля собираются в его папке. `handler.go` владеет handlers и
регистрацией маршрутов модуля; `cmd/api/main.go` только собирает зависимости
и подключает модули к общему router.

## Архитектура

- HTTP handler не содержит бизнес-логики.
- Handler работает по цепочке: `parse → validate → service → response`.
- Service содержит use-case и business logic.
- Repository занимается только persistence.
- Модули не обращаются напрямую к таблицам друг друга.
- Зависимости передаются явно; глобальные DB/Redis clients запрещены.

## Ошибки

- Domain/service возвращают осмысленные errors.
- HTTP mapping ошибок выполняется на boundary — в HTTP-слое.
- Сырой текст ошибки PostgreSQL клиенту не возвращается.

## Context

- `context.Context` — первый аргумент методов, которые обращаются к DB или
  network.
- `context.Context` нельзя хранить внутри struct.

## База данных

- Все изменения схемы выполняются только через `migrations/`.
- SQL не размазывается по handlers.
- Транзакция начинается на уровне use-case, которому действительно нужна
  атомарность.

## API

- Текущий JSON-контракт всегда использует `camelCase`:

  ```json
  {
    "completion": {
      "id": 42,
      "routineId": 7
    },
    "plant": {
      "epoch": 0,
      "phase": 1,
      "phaseProgress": 0.37,
      "branching": 0.48,
      "density": 0.31,
      "curvature": 0.22,
      "vitality": 0.94,
      "seed": 12345
    }
  }
  ```
- Ошибки возвращаются в едином формате.
- ID имеют один тип во всех слоях и модулях.
- Контракт API нельзя менять молча. Если контракт изменится, об этом будет
  сообщено отдельно.

## Код

- Перед коммитом запускать `gofmt` и `go vet`.
- Функции должны быть небольшими и делать одну понятную вещь.
- Интерфейсы вводятся там, где они нужны потребителю, а не «на всякий
  случай».
- Не создавать абстракции ради абстракций.

## Git и code review

- Одна задача — одна ветка.
- PR должен быть небольшим и решать одну задачу.
- Каждый PR другого человека должен посмотреть хотя бы один участник.
- Нельзя пушить напрямую в `main`.
- Если меняется общий контракт, написать об этом в командный чат до merge.

## Если что-то неясно или не успеваешь

Нельзя молча оставлять проблему, делать предположения о критичной логике или
прятать незавершённую работу.

Если не понимаешь задачу, архитектурное решение или последствия изменения —
сначала спроси. Если не успеваешь закончить — заранее сообщи об этом и либо
передай задачу другому человеку, либо явно согласуй перенос срока. Передача
должна включать текущий статус, что уже сделано, что осталось и какие есть
блокеры.
